Section 1The Decision Point

Your robot cruises down the line with confidence—P-control keeping it perfectly centered. Then suddenly: a fork in the road. The line splits. Which way should it go?

In Lesson 8, you taught your robot to follow a line. But real-world line-following courses aren't just straight paths with gentle curves. They have:

  • T-intersections — The line ends with paths going left and right
  • Cross intersections — Lines crossing with multiple path options
  • Dead ends — The line simply stops, requiring a 180° turnaround
📖 A Different Kind of Thinking

This lesson marks a fundamental shift in how your robot operates. In Lesson 8, the robot constantly asked: "How much should I adjust?" — a smooth, continuous calculation. Now at intersections, the question becomes: "Which action should I take?" — a discrete choice between distinct options.

Unlike line following, intersections require the robot to choose between multiple valid actions.

📖 RoboCup Junior Connection

In RoboCup Junior Line Rescue competitions, robots must navigate courses with multiple intersection types. Green markers indicate which way to turn. Miss the marker? You lose points!

📖 Real-World Connection

Self-driving cars face the same challenge at every intersection. The state machine pattern you'll learn today is used in autonomous vehicles, industrial robots, and video game AI!

🔑 Intersection
— A point where the line branches, crosses, or ends, requiring the robot to decide what action to take next.

3.1 How the Robot "Sees" Green

Remember how line sensors work from Lesson 4? They shine infrared (IR) light and measure how much bounces back:

  • White surfaces reflect a lot of IR → Low calibrated values
  • Black surfaces absorb IR → High calibrated values
📖 Why Green Works

Green surfaces absorb some IR light but reflect the rest. This gives us mid-range values (~300–700) that are distinctly different from both white and black.

SurfaceTypical Sensor ValuesClassification
White (floor)< 200 (high reflectance)LOW
Green (marker)~300–700 (medium reflectance)MID (Green!)
Black (line)> 800 (low reflectance)HIGH
🔑 Threshold
— A boundary value used to categorize sensor readings. Values above or below the threshold trigger different behaviors.
💡 TIP
Calibration Required

These threshold values are approximate! Calibrate for YOUR green: expect mid-range values for green, versus black and white at the extremes. The calibration test in Section 7 gives you exact numbers.

3.2 Intersection Types

Green markers are placed beside the line to indicate which way to turn. Your robot detects them with the outer sensors — sensor 1 and sensor 5, which report into array boxes [0] and [4]:

📘 NOTE
What About Cross (+) Intersections?

At a cross intersection, all center sensors see black. Without green markers, go straight by default. Advanced robots use the "right-hand rule" for maze solving (see Challenge 6)!

3.4 What is a State Machine?

🔁 Builds on:
the Variable Speed Test from Lesson 3 — Button B cycling four speeds was a state machine. You built one before you had the name.

Here's a problem: your robot detects green on the left and starts turning. But as it turns, the sensor might briefly see green again. Should it start another turn? This is where a state machine saves the day.

🔑 State Machine
— A programming pattern where a system can only be in ONE specific state at a time, and has defined rules for transitioning between states.

Real-world analogy: think of a traffic light—always in exactly one state (RED, YELLOW, or GREEN), never two at once.

StateWhat the Robot DoesTransitions To
FOLLOWING_LINENormal P-control line following→ AT_INTERSECTION (if green)
AT_INTERSECTIONStop, identify intersection type→ EXECUTING_TURN
EXECUTING_TURNPerform the turn maneuver→ FOLLOWING_LINE (when done)
STOPPEDMotors off, waiting for button→ FOLLOWING_LINE (on press)
💡 TIP
Best Practice: One Action Per State

Keep each state simple—it should do one thing. When in EXECUTING_TURN, the robot ignores new intersection readings. This prevents the "double detection" problem and makes debugging much easier!

3.5 Using Enums for States and Types

We could use plain numbers for states, but that's confusing—state = 0 tells you nothing. A better way is an enum:

🔑 Enum (enumeration)
— A data type that defines a set of named constants. Instead of "0 means following," you just use FOLLOWING_LINE. 
enum RobotState {
    STOPPED,           // Motors off, waiting for B
    FOLLOWING_LINE,    // P-control driving
    AT_INTERSECTION,   // Announcing the decision
    EXECUTING_TURN     // Turning on encoders
};
enum IntersectionType {
    NO_INTERSECTION,   // Plain line - keep driving
    GO_LEFT,           // Green marker on the left
    GO_RIGHT,          // Green marker on the right
    DEAD_END           // Green on BOTH sides
};

3.6 Turn Execution Strategies

There are three ways a robot can execute a 90° tank turn — and you already own the good one:

MethodHow It WorksVerdict
Timed TurnSpin for a fixed number of milliseconds and hope❌ Battery-dependent, surface-dependent — the naive baseline. Not used in this book.
Encoder TurnSpin until the encoders measure the target angle✅ This lesson's method — and you built it in Lesson 6: it's called turnDegrees() and it has been living in RobotMotion.cpp ever since.
Line-Seeking TurnTurn most of the way, then creep until the center sensor finds the line✅ Self-correcting — the competition upgrade. That's Challenge 3.
🔑 Tank Turn
— A turning method where opposite wheels spin in opposite directions, rotating in place. Momentum can cause a little overshoot — encoder turns absorb most of it, and consistent error tunes out via WHEEL_BASE_MM (Lesson 7’s one-number tune-up).
📘 NOTE
The Lesson 6 Dividend

Remember turnDegrees() from Lesson 6? It already turns by encoder counts, already averages both wheels, already ignores battery sag. And it deliberately does not use TRIM — in a pivot the wheels oppose each other on purpose, so there is no straight line to correct. TRIM is for open-loop straight lines; the encoders govern the angle. This lesson's three turn functions are one-line wrappers around it — Step 5 of Section 6 takes about ninety seconds.

5.4 The State Machine Pattern (Pseudocode)

loop:
    SWITCH currentState:
        CASE STOPPED:
            Battery guard, Kp tuning (A / C)
            IF B pressed: countdown, go to FOLLOWING_LINE
        CASE FOLLOWING_LINE:
            IF B pressed: STOP - kill switch outranks everything
            IF line visible:
                followLine()  (all of Lesson 8, one call)
                Ask the outer sensors: any marker?
                IF marker: STOP MOTORS FIRST, save the decision,
                           go to AT_INTERSECTION
            ELSE: handleGap()  (timeout now leads to STOPPED)
        CASE AT_INTERSECTION:
            Announce the decision, pause long enough to read
            Go to EXECUTING_TURN
        CASE EXECUTING_TURN:
            Dispatch the saved decision to the right turn
            Clear it, go back to FOLLOWING_LINE
💡 TIP
Position Bias at Intersections

At T-junctions, readLinePosition() can jump unexpectedly. For reliable detection, read the outer sensors individually — calibrated, of course —. That's why checkForIntersection() reads each sensor for itself!

📖 Avoiding False Positives: Debouncing

Sensor noise can cause brief "false green" readings. Require consistent detection over 2–3 loop cycles for robust detection. See Challenge 5!

// ===== INTERSECTION DETECTION (NEW for Lesson 9) =====

// Is this ONE calibrated reading inside the green band?
bool isGreen(int sensorValue) {
  return (sensorValue >= GREEN_LOW_THRESHOLD &&
          sensorValue <= GREEN_HIGH_THRESHOLD);
}

// Read the outer sensors and answer: what is the course asking for?
IntersectionType checkForIntersection() {
  lineSensors.readCalibrated(sensorValues);   // 0 = white, 1000 = black

  bool leftGreen  = isGreen(sensorValues[0]);   // outermost LEFT sensor
  bool rightGreen = isGreen(sensorValues[4]);   // outermost RIGHT sensor

  if (leftGreen && rightGreen) return DEAD_END;
  if (leftGreen)               return GO_LEFT;
  if (rightGreen)              return GO_RIGHT;
  return NO_INTERSECTION;
}

Section 8AState Machines & Enums

This lesson introduced two professional programming patterns—finite state machines and enums—plus a set of new functions. This section explains the patterns in depth so you can reuse them in any future project.

8A.1 Why Enums Beat "Magic Numbers"

A "magic number" is an unexplained literal in code, like if (state == 2). Six months later, nobody remembers what 2 means. Enums give those numbers names the compiler understands:

// Without enum — what do these numbers mean?
int state = 0;
if (state == 2) { /* ??? */ }
// With enum — self-documenting
RobotState currentState = FOLLOWING_LINE;
if (currentState == EXECUTING_TURN) { /* clear! */ }
📖 Learn/Insight — Enums Are Just Named Integers

Under the hood, the compiler assigns each enum constant an integer (the first is 0, then 1, 2, …). You get readability and the speed of integer comparisons—no trade-off.

8A.2 The Finite State Machine Pattern

A finite state machine (FSM) has three ingredients: a set of states, the current state, and transition rules. The switch (currentState) structure is the standard way to implement one on a microcontroller.

💡 TIP
Each Case Does One Job

A clean FSM case does its work, then decides the next state—nothing more. If a single case is doing five things, it probably needs to be split into more states.

BRAIN CHECK 03 · KNOWLEDGE CHECK — What You Just Built

Your robot reads a marker, picks a turn, and executes it without tripping over itself. These ask whether you know why.

1. Why do green markers show mid-range sensor values? (§3.1)

Green absorbs some of the infrared and reflects the rest, so it lands between the two extremes. On the calibrated 0–1000 scale (0 = your white, 1000 = your black): white reads low (under ~200), black reads high (over ~800), and green sits in the middle band — roughly 300–700, though the only number that matters is the one you survey on your tape.

2. What problem does the state machine solve during turns? (§3.4)

It prevents "double detection" — the robot ignores new intersection readings while in EXECUTING_TURN state.

3. Why are encoder-based turns more reliable than timed turns? (§3.6)

Encoders measure actual wheel rotation, working consistently regardless of battery level or surface friction.

4. What is the advantage of an enum over a plain integer for tracking state? (§3.5)

Named constants are self-documenting and prevent meaningless "magic numbers" in your code. The compiler emits the same numbers either way, so the enum costs nothing at run time — what it buys is that case EXECUTING_TURN: states its own condition, while case 3: makes every reader rebuild it from memory. It also narrows the type: a RobotState variable can only hold one of the four names you declared, so a slip that would have compiled quietly as an int becomes a build error instead of a bug on the course.

do…while — Run First, Then Check

do {
  // body - always runs at least once
} while (condition);   // note the semicolon

// while: test first, so the body may never run
// do..while: act first, so the body always runs once

A while loop checks its condition before the first pass, so if the condition starts false the body never runs at all. A do…while flips the order: the body runs, then the condition is checked.

That matters whenever the condition depends on something the body has to fetch first. In Challenge 3 the test asks whether the center sensor is on black — but nothing has read the sensors yet when the loop is entered, so the array holds stale values. do…while guarantees one read happens before the first test.

  • The trailing semicolon after the condition is required — a plain while loop has none, and leaving it off is the usual compile error.
  • Everything else behaves like while: the loop keeps going while the condition stays true.
  • Reach for it only when the body must run at least once. If a zero-pass run is fine, a plain while is clearer.
