Here's a scenario every robotics student faces:

You write beautiful code. You tell both motors to run at speed 200. You set your robot on the floor, press the button, and watch it drive...

...in a slow, sad curve to the left.

You check your code. Both motors are definitely set to 200. You upload again. Same curve. You try 300. Bigger curve. You try 100. Still curving!

What's going on? Is your robot broken?

Nope. Your robot is completely normal.

Here's the truth that robot manufacturers don't put on the box: no two motors are exactly alike. Even motors from the same factory, made on the same day, have tiny differences in their windings, magnets, friction, and gears. One motor might spin 1% faster than its twin. That doesn't sound like much, but over a few seconds of driving, that 1% adds up to a noticeable curve.

KEY TERM: Motor Imbalance
When two motors don't spin at exactly the same speed despite receiving the same command. Every robot has this.
INSIGHT: Why Does This Happen? (Physics Corner)
Motor imbalance comes from tiny differences in torque (rotational force) — windings, magnets, friction, gear mesh. Give both motors the same command and they settle at slightly different speeds, and there they stay. That is the whole mechanism: not a dramatic force effect, just a small, steady speed gap that the robot spends every second of the run adding up. A wheel turning 1% faster than its partner has traveled a little further after one second, further still after two — and a robot whose tracks have gone different distances is no longer pointing where it started. That is your curve.

Professional roboticists call this motor imbalance, and every wheeled robot on Earth has it—from your Zumo to Mars rovers to warehouse robots at Amazon.

The solution? TRIM.

KEY TERM: TRIM
A small correction value you add to one motor to compensate for imbalance. Think of it like the alignment on a car—you adjust it once, and suddenly your robot drives straight.

3.1 The Two Motors

Your Zumo has two DC motors—one for the left wheels and one for the right wheels. This is called a differential drive system, and it's one of the most common designs in robotics. The Zumo 32U4 Main Board on your Zumo controls both motors, converting your code commands into electrical signals.

A two-motor system where steering is created by running the left and right wheels at different speeds. Used by tanks, wheelchairs, and most small robots.

This simple two-motor system can create any movement: straight lines, curves, spins, and everything in between.

LEARN: How does a motor run BACKWARD?

A DC motor’s direction is set by which way current flows through it — flip the current, flip the spin. The flipping is done by an H-bridge: four electronic switches arranged like the letter H, with the motor as the crossbar. Close the top-left and bottom-right switches and current flows one way through the motor; close the other diagonal and it flows the opposite way.

Your Zumo carries two DRV8838 motor-driver chips — one per motor — each a complete H-bridge that also handles the 20,000-per-second power switching you’ll meet in the next section. So when you write motors.setSpeeds(-200, 200), you’re the commander and the DRV8838s are the muscle: the motors object translates your two numbers into switch patterns on those chips. That’s what an object being a “bridge to the hardware” means — literally, here.

Why do the chips exist at all? Because a microcontroller pin can only supply a few dozen milliamps — wire a motor straight to it and the pin melts. The DRV8838s are heavy-duty switches: they take the microcontroller’s whisper-weak signals and switch the battery’s full current into the motors. Engineers call this whole stack an abstraction layer: you state your intent (setSpeeds(200, 200)), and object → timer → driver chip → motor handles the electrons.

There they are, boxed in gold — two DRV8838 chips, one per motor. Small parts for the job they do: every setSpeeds() you write ends up as switching patterns on these two chips.

3.2 Motor Speed Values

The Zumo library uses a speed range of -400 to +400:

[GRAPHIC 3.12] Speed values at a glance — sign = direction, size = speed, ±400 limits (File: L03_GRAPHIC_3-12_speed_scale.svg)

Understanding Motor Commands: Speed vs. Direction

Here's something important that trips up many beginners: every motor value actually contains TWO pieces of information:

  • Direction — Which way should the motor turn? (Forward or Backward)
  • Speed — How fast should it turn?

We combine these into a single number:

Value Direction Speed In English
200ForwardMedium"Go forward at medium speed"
50ForwardSlow"Go forward slowly"
-200BackwardMedium"Go backward at medium speed"
-50BackwardSlow"Go backward slowly"
0NeitherStopped"Stop"
NOTE
The Key Insight:
The sign (+ or −) controls direction. The size of the number controls speed.

This matters later when you're doing line following: "slow down the left motor" (reduce the number) is very different from "reverse the left motor" (make it negative).
KEY TERM: Negative Speed Values
In everyday speech, you'd say "go backward at speed 5." In code, we use the minus sign instead: -5 means "backward at speed 5." Think of the minus sign as the word "backward"—it flips the direction while the number still tells you how fast.
WARNING
Common Misconception:
Negative does NOT mean "slower"! It means opposite direction.

Every motor value carries both facts at once. The size of the number is the speed; the sign is the direction:
  • 200 → size 200, sign + → speed 200, forward
  • -200 → size 200, sign − → speed 200, backward
Same speed. Opposite directions. So motors.setSpeeds(-200, 200) runs both motors at speed 200 — one forward, one backward — and the robot spins in place.
NOTE
Think of a Number Line
If negative numbers feel weird, picture a number line:
  • Zero is stopped
  • Moving right (positive) is forward
  • Moving left (negative) is backward
  • The farther from zero, the faster you go
[GRAPHIC 3.17] The number line — negative is backward, zero is stopped, positive is forward (File: L03_GRAPHIC_3-17_number_line.svg)
// 💻 CODE EXAMPLES
motors.setSpeeds(200, 200); // Both forward at half speed
motors.setSpeeds(-200, -200); // Both backward at half speed
motors.setSpeeds(200, -200); // Spin right (left fwd, right back)
motors.setSpeeds(0, 0); // Stop both motors
NOTE
The actual wheel speed depends on your battery voltage. At full charge, speed 200 might move faster than speed 200 with low batteries. This is one limitation of "open-loop" control—we'll learn to overcome it with encoders in a later lesson.
LEARN: What IS a “speed of 200,” physically?

It’s not 200 of anything you can put a unit on — no volts, no RPM. The motor driver can really only do two things: power fully ON, or fully OFF. So it fakes everything in between by switching ON and OFF 20,000 times per second and controlling what fraction of each cycle is ON. That fraction is called the duty cycle, and the technique is PWM — Pulse Width Modulation.

Your speed number is just the duty-cycle dial: 400 = ON 100% of the time (full power) · 200 = ON half of each cycle (≈50% power) · 0 = never ON. The sign picks the current direction (forward/backward). The motor spins smoothly instead of stuttering because 20,000 pulses per second is far too fast for a physical armature to follow — it averages them out. And 20 kHz is chosen for your ears’ sake: switching any slower would produce an audible whine.

And here’s the part that should impress you: your code isn’t doing any of that switching. The library programs Timer 1 — a dedicated 16-bit timer circuit inside the ATmega32U4 — to generate the pulses in hardware, forever, with zero attention from your program. That’s why loop() stays free to watch buttons while both motors run: the chip has a specialist doing the 20,000-per-second work.

3.3 Open-Loop vs. Closed-Loop Control

KEY TERM: Open-Loop Control
Send a command and hope for the best. No feedback about what actually happened.

When you call motors.setSpeeds(200, 200), you're telling the Zumo 32U4 Main Board to apply a certain amount of power to the motors. But you have NO feedback about:

  • How fast the wheels are actually spinning
  • Whether both wheels are spinning at the same speed
  • Whether the robot is actually going straight

It's like driving a car blindfolded. You can turn the steering wheel, but you can't see if you're staying in your lane.

KEY TERM: Closed-Loop Control
Send a command, measure the result, and adjust. The "loop" closes because information flows back from the wheels to the controller.

With encoders (which we'll add in Lesson 6), the robot can measure actual wheel rotation and automatically adjust motor power to maintain the desired speed. That's closed-loop control.

For now, we're stuck with open-loop. But don't worry—with proper TRIM values, open-loop control works surprisingly well for basic navigation.

LEARN: Driving blind has a name — dead reckoning

Your TRIM Finder drives “by the clock”: run the motors at speed X for time T and hope that adds up to the distance you wanted. Navigators call this dead reckoning — estimating where you are from speed × time, without ever checking. Ship captains crossed oceans this way for centuries, and it has the same flaw on your desk as it did at sea: every small error (friction, battery level, momentum, a dusty patch of floor) quietly accumulates, and nothing ever corrects it. Keep that word in your pocket — in Section 3.6 you’ll catch dead reckoning failing red-handed, and in Lesson 6 you’ll meet the sensor that fixes it.

3.4 Why Robots Don't Drive Straight

Even with identical speed commands, your robot will drift because of:

1. Motor Manufacturing Differences

  • Tiny variations in copper windings
  • Slight differences in magnet strength
  • Variations in bearing friction
  • Gear tooth imperfections

2. Mechanical Factors

  • Wheel diameter differences (even 0.1mm matters!)
  • Uneven weight distribution
  • Different floor surfaces under each wheel
  • Debris on wheels or tracks

3. Electrical Factors

  • Resistance variations in wiring
  • Battery position affecting weight distribution

The good news: most of these factors are consistent for YOUR robot. Your left motor is always a little faster (or slower) than your right. Once you measure this difference, you can correct for it.

3.5 The TRIM Concept

TRIM is a correction value that compensates for motor imbalance.

Example: Your robot curves left, meaning the left motor is weaker (or the right is stronger) — a robot always turns toward its slower side.

// Without TRIM:
motors.setSpeeds(200, 200); // Robot curves left 😞
// With TRIM (let's say TRIM = 15):
motors.setSpeeds(200 + 15, 200); // Left: 215, Right: 200
// Now the robot drives straighter! 🎉

By adding a small boost to the weaker motor, we balance them out.

Why always the LEFT motor? Because TRIM has to mean the same thing on every robot in the room and in every lesson for the rest of the year. Pick one wheel and stay on it, and a single number tells the whole story: positive boosts the left, negative eases the left down. If you corrected whichever side happened to be weak, the same TRIM value would mean opposite things on two robots — and every table, tip and troubleshooting row after this page would need to ask which one you chose first.

TRIM values guide:

Robot Curves... Problem TRIM Needed
LEFTLeft motor weakPOSITIVE (+5, +10...)
RIGHTRight motor weakNEGATIVE (-5, -10...)
STRAIGHTMotors balanced!ZERO (lucky you!)

Typical TRIM values range from -30 to +30. If your TRIM is larger than ±50, something might be wrong with your robot's hardware.

TIP
TRIM Isn't Perfect (And That's Okay!)

Your TRIM value will change depending on:

  • Speed setting — A TRIM that works at speed = 200 might not work at speed = 400
  • Battery level — As the NiMH pack slides from its 4800 mV plateau toward the 4200 mV floor, motor behavior shifts (Section 3.6)
  • Surface friction — Carpet vs. tile vs. competition mats all behave differently

If your robot still curves slightly after calibration, don't spend hours perfecting it! We'll fix drift permanently in Lesson 6 using encoder feedback. For now, "close enough" is good enough.

TIP
Write your TRIM value on a piece of tape and stick it to your robot — and write it in your notebook too. Every robot is different, and you'll need this number for every future lesson. The tape can fall off; the notebook is your backup. Some students even write it in permanent marker on the battery compartment.

3.6 Battery Voltage: The Hidden Variable

Your robot's behavior changes as batteries drain:

Why this matters:

  • Speed changes: The same speed command produces different actual speeds at different voltages
  • TRIM may shift: Your carefully calibrated TRIM might be slightly off with fresh vs. old batteries
  • Competition consistency: If you calibrate with fresh batteries but compete with half-dead ones, your robot will behave differently

The solution: The Zumo can measure its own battery voltage! We'll use readBatteryMillivolts() to monitor battery health.

int voltage = readBatteryMillivolts(); // Returns voltage in millivolts
// Fresh NiMH (4 cells) ≈ 5400 mV
// Healthy plateau  ≈ 4800 mV
// Recharge below   ≈ 4200 mV
Unit Conversion: Millivolts to Volts
The function returns millivolts (mV), which is 1/1000 of a volt:
  • 5400 mV = 5.4 V (divide by 1000)
  • 4800 mV = 4.8 V
  • 4200 mV = 4.2 V
To convert: Volts = Millivolts ÷ 1000

Battery voltage reference:

Reading NiMH — what our robots run What to do
5,400 mVFresh off the charger (~1.35 V per cell)Go. Best runs of the day.
4,800 mVThe plateau — 1.2 V per cell, where NiMH spends most of its lifeNormal working range. Your tuning holds here.
4,200 mV1.05 V per cell — nearly emptyRecharge. Draining NiMH below this damages the cells.
6,300 mVNot NiMH at all — somebody put alkalines inWorks, but read the box below before you tune anything.
Which cells — and why the code says 4800 and 4200

Our robots run rechargeable NiMH cells (Panasonic eneloop): 1.2 V each, 4.8 V for four. Alkalines give 1.5 V each — 6.0 V — which is actually the voltage the Zumo’s motors are rated for, so a robot on fresh alkalines is a little faster. So why do we use NiMH?

Because of the shape of the discharge, not the height of it. Panasonic’s own measurements say it plainly: a NiMH cell holds a steady 1.2 V for nearly the whole charge and then drops off; an alkaline starts at 1.5 V and slides downhill the entire time it is used. A robot on alkalines is a moving target — the one you tuned in first period is not the one you get in seventh. A robot on NiMH is the same robot all day, and then tells you plainly when it is done.

That is where the numbers in your code come from. 4800 is four cells sitting on their plateau. 4200 is 1.05 V per cell — empty, and the floor below which the cells take damage. They are not arbitrary. They are the chemistry.

Alkalines get exactly one honest use: a competition run where you want the motors at their rated 6 V — knowing you tuned on a target that was moving the whole time.

TIP
For competition, always start with fresh batteries AND re-verify your TRIM. The 5 minutes spent checking calibration can save you from embarrassing curved driving during a match.

3.7 The Motor Test Strategy

NOTE
First, a unit: milliseconds.
Every timing number in this lesson is in milliseconds (ms) — thousandths of a second. So 1000 ms = 1 second. That means TEST_DURATION = 2000 runs the motors for 2 seconds, and a delay(500) is a half-second pause. Whenever you see delay(...) from here on, read the number as milliseconds.

To find your TRIM value, we'll use this process:

Step 1: Baseline Test

  • Set both motors to the same speed (e.g., 200)
  • Place robot on a long, flat surface
  • Watch which direction it drifts

Step 2: Identify the Problem

First, whose left? Always the robot’s — its blade is the front. If it is driving away from you, you are seeing its back, and its left is on your right. Stand behind the robot, or turn your head to face the way it is facing, before you decide which way it curved. This one is the most common way a TRIM hunt goes backwards.

  • Curves LEFT → LEFT motor is weak → Need POSITIVE TRIM (boosts the left)
  • Curves RIGHT → RIGHT motor is weak → Need NEGATIVE TRIM (eases the left down to match)
  • Drives straight → You're done! (TRIM = 0)

Step 3: Adjust and Repeat

  • Add TRIM in increments of 5-10
  • Test again
  • Repeat until robot drives acceptably straight
NOTE
Why 5 or 10, not 1 or 2?
A change of 1 or 2 is usually too small to see over a short test run — the robot drifts about the same, and you waste a whole run learning nothing. Steps of 5–10 make a visible difference each time, so you close in on the right value in a few runs instead of a dozen. Once you are close, you can drop to steps of 2–3 to fine-tune.

Step 4: Verify at Different Speeds

  • Test at speed 150, 200, 250, 300
  • TRIM should work reasonably well across all speeds
  • If not, use an average that works "okay" everywhere

Step 5: Document

  • Write down your final TRIM value in your notebook
  • Note which batteries you used
  • Save this in your code as a constant

3.8 The setSpeeds() Function

The main motor control function:

[GRAPHIC 3.11] Anatomy of a command — object . method ( arguments ) ; broken into its four parts (File: L03_GRAPHIC_3-11_command_anatomy.svg)
motors.setSpeeds(leftSpeed, rightSpeed);

Parameters:

  • leftSpeed: -400 to +400 (negative = backward)
  • rightSpeed: -400 to +400 (negative = backward)

Important behaviors:

  • Speeds are applied immediately — no delay needed
  • Speeds persist until changed — motors keep running until you call setSpeeds() again
  • Always stop your motors — call motors.setSpeeds(0, 0) when done!

Common patterns:

// Drive forward
motors.setSpeeds(200, 200);
// Drive backward
motors.setSpeeds(-200, -200);
// Spin right (in place)
motors.setSpeeds(200, -200);
// Spin left (in place)
motors.setSpeeds(-200, 200);
// Gentle curve right
motors.setSpeeds(200, 150);
// STOP (always do this!)
motors.setSpeeds(0, 0);
ALWAYS STOP YOUR MOTORS.
This is the single most common bug we see — the same one that bites teams in VEX. Speeds persist: once you call setSpeeds(), the motors keep running at that speed until you tell them otherwise. If your program ends, loops, or waits without a motors.setSpeeds(0, 0), the robot drives off the table. Make stopping a habit: every time you start the motors, know where they stop.
LEARN: Three ways to "stop" — coast, brake, hold

"Stop" is not one thing. In robotics there are three different stops, and they feel different:

  • Coast — cut the power and let the robot roll to a halt on its own. Smooth, but it drifts past the spot. (Electrically: the motor leads are left open.)
  • Brake — short the motor across itself so it resists turning and stops quickly. Less drift, a harder stop.
  • Hold — actively drive toward "stay here," fighting anything that tries to push the robot. Uses power even while standing still.

On the Zumo, setSpeeds(0, 0) gives you a brake-style stop — the driver shorts the motors, so the robot stops promptly rather than coasting. That is usually what you want for precise moves. Keep the three in mind: when a robot "won't stop where I told it," the question is often which kind of stop you actually used.

3.9 The constrain() Function

When calculating motor speeds with TRIM, you might accidentally exceed the -400 to +400 range. The constrain() function keeps values within safe limits:

int speed = 380;
int trim = 30;
int leftSpeed = speed + trim; // 410 - TOO HIGH!
// Use constrain to keep it safe:
leftSpeed = constrain(speed + trim, -400, 400); // Now it's 400
KEY TERM: constrain(value, min, max)
Returns: min if value < min, max if value > max, otherwise returns value unchanged. Keeps values within a safe range.
Where Does constrain() Come From?
The constrain() function is part of the Arduino core library (Arduino.h), which is automatically included when you use the Zumo32U4 library. You don't need to include anything extra—it just works!

This returns:

  • minimum if value < minimum
  • maximum if value > maximum
  • value if it's already in range
TIP
Always use constrain() when adding TRIM or calculating speeds dynamically. It keeps your speed math honest.

Does it really matter, if the library caps at 400 anyway? Fair question — and yes, setSpeeds() already clamps anything past ±400 internally, just like a VEX motor maxes out no matter what number you feed it. So constrain() is not there to protect the motor. It matters when you use the speed number for something else — showing it on the display, logging it, or feeding it into more math — where an out-of-range value (like 415) would be wrong or confusing. Constrain your own variables so the number you see and the number the motor gets are the same.

3.10 Safety Considerations

Motors can make your robot do unexpected things. Always follow these rules:

1. Start with LOW speeds

  • Test new code at speed 100-150 first
  • Increase speed only after code works correctly

2. Have a STOP plan

  • Keep your finger near the power switch
  • Know which button stops the motors (we'll program this)
  • Test on the floor, not on tables

3. Give yourself space

  • Clear area of at least 3 feet in all directions
  • Remove obstacles, drinks, and sleeping pets
  • Tile or wood floors work best (carpet can stall motors)

4. Watch for runaways

  • If motors spin unexpectedly, HIT THE POWER SWITCH
  • Never try to grab a moving robot by the wheels
  • If code has a bug, motors might never stop on their own
NOTE
3Pi+ Note:
The 3Pi+ has more powerful motors than the Zumo. Use lower speed values (start at 100) and expect more aggressive acceleration. Your TRIM value for a 3Pi+ will likely be different from a Zumo.

3.11 TRIM Math (Optional Deep Dive)

Want to understand the math behind TRIM? Here's how it works:

If your right motor is running X% faster than your left motor, you need to boost the left motor by approximately:

TRIM ≈ BASE_SPEED × (X / 100)

Example:

  • Your right motor is about 5% faster than your left
  • You're testing at BASE_SPEED = 200
  • TRIM ≈ 200 × 0.05 = 10

So you'd use motors.setSpeeds(210, 200) to balance them.

🔢 Working Backward:
If you found TRIM = 15 at speed 200, your motor imbalance is approximately:

Imbalance % = (TRIM / BASE_SPEED) × 100 = (15 / 200) × 100 = 7.5%

This means one motor is about 7.5% weaker than the other—totally normal!

You don't need to calculate this—trial and error works fine. But understanding the math helps explain why TRIM changes slightly at different speeds.

LEARN: Inside the little silver can

Each motor is an electromagnet trick: coils of wire sit inside permanent magnets, and running current through the coils makes them push against the magnets and spin. A tiny switch called a commutator flips the current direction every half-turn so the push never runs out — that’s the whole secret of a brushed DC motor.

Bare, that motor spins thousands of RPM with almost no strength — it couldn’t push a pencil. The gearbox stacked on its nose is a chain of small-gear-drives-big-gear stages that divides the speed and multiplies the torque by the same factor (Pololu builds the Zumo in three gear ratios — 50:1, 75:1, and 100:1 — see the specs below). Roughly: the motor shaft spins dozens of times for every one turn of the track sprocket — and in exchange, your 275-gram robot can shove things many times its own weight.

[GRAPHIC 3.18] Inside the gearbox — side view shows the gears meshing; the cutaway shows how they ladder on stepped shafts (File: L03_GRAPHIC_3-18_gear_train.svg)

The motor, out in the open. The silver can is the motor itself; the gearbox stacked on its nose is the stack of gears that trades speed for torque. Its output turns the sprocket that drives the track.

Brushed vs. brushless — why yours has brushes. The commutator trick has a catch: something has to physically touch the spinning shaft to flip the current. That something is a pair of small contacts called brushes, and they rub. Rubbing means friction, sparks, electrical noise, and parts that slowly wear away. Your Zumo's motors are brushed.

A brushless motor deletes them. The magnets spin, the coils stay still, and an electronic controller switches the coils in the right order at the right instant — the commutator becomes a circuit instead of a contact. Nothing rubs, so brushless motors run cooler, last far longer, and waste less of your battery. That is why drones, e-bikes, computer fans and modern cordless drills are all brushless.

The trade is complexity. A brushed motor needs only two wires and a voltage, and reversing that voltage reverses the motor — which is exactly what the DRV8838 does when you write motors.setSpeeds(-200, -200). A brushless motor cannot be driven that way at all; it needs three wires and a controller of its own. For a robot this small and this cheap, brushed wins.

Motor specifications (Zumo 32U4):

  • Gear ratio: 75:1 on most robots — 75 motor rotations = 1 sprocket rotation
  • Operating voltage: 3-6V (from 4 AA batteries)
  • Stall current: ~1.5A per motor (if wheels are blocked)
  • Robot weight: ~275 g with batteries (~170 g without)
NOTE
Not every Zumo has the same gears.
Pololu sells the Zumo with three different gearboxes, and they behave differently: 50:1 is the fastest and weakest, 75:1 is the middle (and what most classroom robots run), 100:1 is the slowest and strongest. Same code, same speed number, different robot — a 50:1 robot travels noticeably farther in the same 2 seconds than a 100:1 robot does.

How to tell which one you have: take the batteries out and look inside the battery compartment. There is a colored sticker on the underside of the main board, and its color tells you the gear ratio (this is Pololu's own code):

Green = 50:1  Blue = 75:1  Red = 100:1

Most classroom robots have the blue (75:1) sticker. If two robots in the room disagree about how far "speed 200 for 2 seconds" goes, check the stickers before you blame the code — a different color means a different gear ratio.
WARNING
Stall current — the two ways it bites.
A motor draws the most current when it is trying to turn but can't — that maximum is the stall current (about 1.5 A per motor on the Zumo, roughly 5× its free-running draw). It shows up in two situations that look different but are the same electrical event:

1. You hold the wheels (or the robot is jammed against a wall). The motor fights to move, can't, and dumps that energy as heat. Hold it there and you cook the motor. Never stall for more than a few seconds.

2. The robot is too heavy or geared wrong to move at all. Same thing — the motor is pulling stall current but the robot just sits there. On our non-sumo RoboCup bots this is the usual "it won't move" culprit: the motor is powered, it simply can't overcome the load, so it sits at stall drawing max current and going nowhere. If a robot buzzes/strains but doesn't move, cut power — it is stalling, and it is heating up.
WARNING
Motor Heat Warning:
Motors heat up from current, and current comes from load — not from the number in your code. A motor spinning freely at 400 draws very little. A motor at 150 with a track jammed or a wheel held draws close to its stall current and can cook its own windings in seconds, which is why the rule above is to cut power the moment a robot strains without moving. So the thing to avoid is a loaded motor, not a stopwatch reading. If the motors feel warm to the touch, let them rest before the next run.

4.3 Battery Monitoring

The Zumo 32U4 Main Board can read its own battery voltage using:

This returns the voltage in millivolts (1/1000 of a volt). See Section 3.6 for the voltage reference table.

Accuracy Note:
readBatteryMillivolts() is an estimate, not a laboratory measurement. Read it with the motors OFF. It is good at telling "fresh" from "low," which is all this lesson asks of it; it is not a precision voltmeter.

5.3 How TRIM Works (the core idea)

TRIM is one number that fixes a crooked robot. Both motors should run at the same speed, but tiny manufacturing differences make one wheel slightly faster — so the robot curves. Instead of rebuilding the hardware, you correct it in software by nudging one wheel:

// PSEUDOCODE: how TRIM is applied
leftSpeed  = BASE_SPEED + trimValue;     // left wheel = baseline + correction
rightSpeed = BASE_SPEED;                 // right wheel = baseline
motors.setSpeeds(leftSpeed, rightSpeed);

If the robot veers left, the left wheel is too slow → raise trimValue (positive). If it veers right, lower it (negative). Each button press changes trimValue by TRIM_STEP, so you converge on "straight" by trial and observation. This is your first taste of manual iterative tuning: change a value, observe, adjust.

KEY TERM: TRIM
A single adjustable value added to one motor's speed to compensate for mechanical imbalance, making a robot drive straight without changing hardware.

5.5 Writing a Decision: if, Comparison, and the One-Character Trap

Lesson 2 taught you to read an if statement: a question in parentheses, a block in braces, an optional else for the other answer. Section 9 asks you to write one from a blank line, which is a different skill. Here is the whole move.

Start with the sentence. Say what you want in plain English, with the word “if” in it: “If the test speed is above 400, print a warning.” Now translate it left to right — the sentence and the code are in the same order:

if (testSpeed > 400) {
  Serial.println(F("Too fast for this classroom!"));
}

The only genuinely new piece is the middle: testSpeed > 400. That is a comparison, and it is how a number becomes a yes/no answer the if can use. Six of them cover everything you will need:

OperatorAsksTrue when…
>greater thanleft is bigger — 500 > 400
<less thanleft is smaller — 300 < 400
>=greater than or equalbigger or exactly equal — the boundary counts
<=less than or equalsmaller or exactly equal
==is equal tothe two values match — note the TWO equals signs
!=is not equal tothe two values differ

Decide the boundary on purpose. > and >= differ by exactly one case — the value sitting on the line — and that one case is where robot bugs like to live.

WARNING
The one-character trap: = is not ==

One equals sign assigns: put this value in that box. Two equals signs compare: are these two the same? Different jobs, one keystroke apart — and this is the most expensive typo in the language, because neither direction is an error. Both compile. Both run. Both do the wrong thing quietly.

Direction 1 — you meant to compare and typed one equals:

if (trimValue = 5) {     // WRONG: this ASSIGNS 5 to trimValue
  motors.setSpeeds(0, 0);
}

Two things just went wrong, and the screen tells you about neither. Your TRIM was overwritten with 5. And the if now tests the value 5, which C++ treats as true — so the block runs every single time, forever, no matter what TRIM was.

Direction 2 — you meant to assign and typed two:

trimValue == 5;              // WRONG: this COMPARES, then throws the answer away

The comparison happens, produces true or false, and nothing catches it. trimValue never changes. You will swear you set it, and the robot will swear you did not, and the robot is right.

The habit that saves you: when a condition behaves like it is stuck — always firing, or never firing — count the equals signs before you question your logic. Inside if (…), a single = is almost always a typo.

Two more shapes, and you have the full set. Add else when there is a plan for “no,” and chain else if when there are more than two outcomes:

if (testSpeed > 400) {
  Serial.println(F("Too fast"));
} else if (testSpeed < 50) {
  Serial.println(F("Too slow to move"));
} else {
  Serial.println(F("Good testing speed"));
}

They are checked top to bottom and exactly one branch runs — the first one whose answer is yes. Once a branch fires, the rest are skipped without even being asked. That is why order matters: put the narrowest condition first, or a broader one above it will answer for it.

5.6 Three Ways to Say “Add One” (They Are All the Same)

You will see a counter go up written three different ways across this book — in the lessons, in the reveals, in your classmates’ code. They look different and they do exactly the same thing. Meet all three now so none of them trips you later.

Say testCount holds 4 and you want it to hold 5. Every line below does that, and only that:

Written asRead it asWhen you’ll reach for it
testCount = testCount + 1;“the new count is the old count plus one”the long form — clearest the first time, spells out every piece
testCount += 1;“add one to count”the shorthand — and it takes any number, so += 10 adds ten
testCount++;“bump count by one”the shortest — but only ever adds 1, nothing else

You have already used the last one without a second thought: i++ is what steps a for loop from one pass to the next. Same operator, out in the open here.

The rule of thumb

++ when you are adding exactly 1 (loop counters, tallying presses). += n when you are adding some other amount (nudging TRIM by 5, a score by 10). The long form when you are learning the line or want it to read like a sentence. Pick whichever is clearest — the robot cannot tell them apart, so write for the human who reads it next.

Two things to keep straight. There is no ++ for anything but 1 — if you need to add 5, it is += 5, not +++++. And subtraction mirrors all three exactly: count = count - 1, count -= 1, and count-- are the same three spellings going the other way.

1. Why don’t robots naturally drive straight, even with identical code for both motors? (§3.4)

No two motors are identical — tiny manufacturing differences in windings, brushes, gear friction, and even tire grip mean the same power command produces slightly different wheel speeds. The robot curves toward the slower side.

2. What does “open-loop control” mean, and what’s its core limitation? (§3.3)

Open-loop = the robot sends commands but never measures what actually happened — no feedback. Its limitation: it can’t notice or correct error. TRIM helps, but it’s a fixed guess; it can’t adapt when conditions change.

3. How does differential drive create turns and spins with only two motors? (§3.1)

Different speeds on the two tracks: one faster than the other = a curve toward the slower side; equal and opposite (setSpeeds(200, -200)) = a spin in place around the robot’s center.

4. What does a negative value in setSpeeds() mean — and what does it NOT mean? (§3.2)

Negative = that motor runs backward. It does NOT mean “slower” — -400 is full speed in reverse. The number’s size is the speed; its sign is the direction.

5. What does constrain(value, -400, 400) protect you from? (§3.9)

Out-of-range speed values. After TRIM math, a number can exceed the legal ±400 range; constrain() clamps it back inside the limits so the motor library always receives a valid command.

// ===== LOOP =====
void loop() {
  // The instant the Serial Monitor connects, print the banner (once)
  if (!instructionsPrinted && Serial) {
    printInstructions();
    instructionsPrinted = true;
  }

  // Check for A+C held together (reset TRIM)
  if (buttonA.isPressed() && buttonC.isPressed()) {
    trimValue = 0;
    blinkConfirm();
    delay(100);
    blinkConfirm(); // Double blink for reset
    Serial.println(F("[RESET] TRIM set to 0"));
    printTrimAdvice();
    updateDisplay();
    delay(500); // Debounce
  }
  // Button A: Decrease TRIM
  else if (buttonA.getSingleDebouncedPress()) {
    trimValue -= TRIM_STEP;
    trimValue = constrain(trimValue, -50, 50);
    blinkConfirm();
    Serial.print(F("[BTN A] TRIM decreased to "));
    Serial.println(trimValue);
    printTrimAdvice();
    updateDisplay();
  }
  // Button B: Run motor test
  else if (buttonB.getSingleDebouncedPress()) {
    blinkConfirm();
    Serial.println(F("[BTN B] Starting motor test..."));
    runMotorTest();
  }
  // Button C: Increase TRIM
  else if (buttonC.getSingleDebouncedPress()) {
    trimValue += TRIM_STEP;
    trimValue = constrain(trimValue, -50, 50);
    blinkConfirm();
    Serial.print(F("[BTN C] TRIM increased to "));
    Serial.println(trimValue);
    printTrimAdvice();
    updateDisplay();
  }
  delay(10);
}

Section 8ATuning with Calibration Constants

In this lesson you nudged trimValue until your robot drove straight. That wasn't a one-off trick — it's a pattern you'll reuse in almost every lesson ahead. This section names it so you can spot it and apply it deliberately.

8A.1 The Pattern: Name It, Don't Bury It

A calibration constant is a value you'll want to adjust later, given a name and parked at the top of your program. The opposite — a "magic number" — is a raw value buried mid-code:

// ❌ Magic number — what is 205? why 200? where do I change it?
motors.setSpeeds(205, 200);
// ✅ Calibration constants — named, tunable, in one place
const int BASE_SPEED = 200;
const int TRIM_STEP  = 5;
motors.setSpeeds(BASE_SPEED + trimValue, BASE_SPEED);

Both run identically. The difference is for the human: when you need to change the speed, you change one named line at the top instead of hunting for stray numbers.

TIP
A good test — if you'd have to explain a number to a teammate ("oh, 205 is the left wheel with trim baked in"), it should be a named constant, not a literal.

8A.2 Constant vs. Variable: Which One?

Two kinds of tuning values, and choosing right prevents bugs:

Use a const when… Use a variable when…
The value is fixed for the whole run (BASE_SPEED, TRIM_STEP)The value changes while running (trimValue, testCount)
You set it once and never reassignYou update it in response to buttons, sensors, time
Accidental change should be an errorChange is the whole point

Marking a fixed value const tells the compiler "this must never change" — so if you accidentally try to reassign it, you get caught at build time instead of chasing a weird bug later.

8A.3 The Tuning Loop

Calibration constants exist because of a workflow you'll repeat all year:

1. Set a starting value      (const int TRIM_STEP = 5;)
2. Run the robot, observe    (does it drive straight?)
3. Adjust the value          (too coarse? TRIM_STEP = 2)
4. Repeat until good enough

This is human-in-the-loop tuning — you are the feedback loop now; later, sensors will be. The reason your tunables sit together at the top is so step 3 takes five seconds, not five minutes.

INSIGHT:
Every robot you'll ever build has "knobs" — speeds, thresholds, timings, gains. Pros put all the knobs in one labeled box at the top of the file. You just built your first knob (TRIM_STEP); in Lesson 8 you'll tune a control gain the exact same way.

8A.4 Naming That Survives

A calibration constant is only useful if its name explains itself months later:

Weak Strong Why
int s = 200;const int BASE_SPEED = 200;Says what it controls
int t = 5;const int TRIM_STEP = 5;Says what changes by it
int d = 2000;const int TEST_DURATION = 2000;Says it's a time, and what for

Use ALL_CAPS for constants by convention — it signals "this is a fixed knob" at a glance, distinct from regular camelCase variables.

8A.5 When One Knob Becomes Several: Arrays

Every tunable so far has been a single named value. Sometimes you want to try several in a row — four test speeds, three thresholds — and naming them TEST_SPEED_1 through TEST_SPEED_4 gets ugly the moment you want to step through them.

An array is one name holding a numbered row of values. The [] after the name is what makes it a row instead of a single value:

const int TEST_SPEEDS[] = {150, 200, 250, 300};
const int NUM_SPEEDS = 4;   // how many slots — worth naming, you will need it

You read one slot by its number, in square brackets:

TEST_SPEEDS[0]   // 150  <-- the FIRST slot
TEST_SPEEDS[1]   // 200
TEST_SPEEDS[2]   // 250
TEST_SPEEDS[3]   // 300  <-- the LAST slot

Counting starts at zero. Four values live in slots 0, 1, 2 and 3 — there is no slot 4. Every programmer trips on this once; the rule is that the last slot is always one less than the count.

WARNING
reading past the end — TEST_SPEEDS[4] on a four-slot array — is not an error. C++ does no bounds checking on an AVR: it reads whatever bytes happen to sit after your array and hands them back as a number. Your robot then drives at a speed you never wrote. This is why the wrap in 8A.6 matters.

The payoff is that the slot number can be a variable. One line then reads a different speed depending on what that variable holds:

int speedIndex = 1;
int currentSpeed = TEST_SPEEDS[speedIndex];   // 200 — because speedIndex is 1

8A.6 Wrapping Around: the % Operator

Once an index can move, it has to come back. Advance speedIndex four times on a four-slot array and it is pointing at slot 4, which does not exist. The obvious fix needs an if:

speedIndex = speedIndex + 1;
if (speedIndex >= NUM_SPEEDS) {
    speedIndex = 0;
}

There is a one-line version. The % operator — modulo — gives you the remainder of a division rather than the division itself:

7 % 3   // 1   — 3 goes into 7 twice, with 1 left over
6 % 3   // 0   — divides evenly, nothing left over
2 % 4   // 2   — 4 does not fit at all, so all of it is left over

The property that makes it useful: a remainder can never be as large as the number you divide by. So something % 4 is always 0, 1, 2 or 3 — which is exactly the set of legal slot numbers for a four-slot array. Advancing and wrapping become one line:

speedIndex = (speedIndex + 1) % NUM_SPEEDS;   // 0 -> 1 -> 2 -> 3 -> 0 -> 1 ...

No if, and no way to run off the end — the operator makes the out-of-range value from 8A.5 unreachable by construction.

TIP
the parentheses are load-bearing. % binds tighter than +, so speedIndex + 1 % NUM_SPEEDS is read as speedIndex + (1 % NUM_SPEEDS) — and since 1 % 4 is just 1, that line adds one forever and never wraps. Write (speedIndex + 1) % NUM_SPEEDS.

  display.print(F("B=run"));
}

void setup() {
  showSpeed();
}

void loop() {
  if (buttonA.getSingleDebouncedPress()) { testSpeed -= 5; showSpeed(); }
  if (buttonC.getSingleDebouncedPress()) { testSpeed += 5; showSpeed(); }
  if (buttonB.getSingleDebouncedPress()) {
    motors.setSpeeds(testSpeed, testSpeed);
    delay(1000);
    motors.setSpeeds(0, 0);
  }
}
🔓 Hint: what you’ll observe

Below some threshold the motors hum but nothing moves — the electromagnets are pushing, but static friction in the gears and treads wins. That threshold is different for every robot (and every battery level!). This is why real robot code often has a MINIMUM_SPEED constant.

🔓 Hint + what’s going on

Change the two setSpeeds lines inside the test to use negative values, and leave the TRIM math exactly as it is. Then watch carefully: most robots curve worse backward than they did with no TRIM at all.

That is not the gearbox. That is your correction pointing the wrong way. With BASE_SPEED = 200 and TRIM = 15, forward you are sending setSpeeds(215, 200) — the weak left motor gets more. Negate both and you are sending setSpeeds(-185, -200). The library takes the size of each number and puts the minus sign on a direction pin, so the left motor is now getting 185 against 200 — less than the right, when it needed more. You have not removed the correction; you have aimed it backwards, which is roughly twice as bad as having none.

Fix that and the big curve goes away. A small one may remain, and that part really is mechanical — gearboxes and treads are not perfectly symmetric in the two directions, which is why real rovers sometimes store a separate calibration per direction. But that is the fine print, not the headline. Lesson 6 is where the code has to start caring: driveDistance() takes a distance that can be negative, so it is the first function that has to make one TRIM number serve both directions.

Zumo32U4ButtonA buttonA;

void setup() {
}

void loop() {
  if (buttonA.getSingleDebouncedPress()) {   // A = slam stop
    motors.setSpeeds(400, 400);
    delay(1500);
    motors.setSpeeds(0, 0);
  }
  if (buttonC.getSingleDebouncedPress()) {   // C = ramp-down stop
    motors.setSpeeds(400, 400);

    }
  }
}
🔓 What you’re measuring

Even the “instant” stop skids — a 400-speed robot carries momentum, and rubber treads on smooth floor can’t dump it instantly. The ramp-down travels farther by design but is controlled the whole way (and gentler on the gearbox — real robots almost never slam from full speed to zero). Look closely at that loop: it counts down (s = 400, test s >= 0, step s -= 20), and the counter is the speed rather than a lap tally. You have only met loops that count up by one; you will take the descending form apart properly in Lesson 5. Here it is your first deceleration profile — Lesson 6 turns this idea into real motion control.

You’d expect swapping the speeds to mirror the circle perfectly. Expect to tune each circle’s speed pair and duration separately. If your eight closes within a hand-width, that’s genuinely good for open-loop driving.

Glossary
Closed-Loop Control
Send a command, measure the result, and adjust. The "loop" closes because information flows back from the wheels to the controller. See Section 3.3.
constrain(value, min, max)
A function (from Arduino.h) that keeps a value within a specified range. Returns min if value is too low, max if too high. See Section 3.9.
Differential Drive
A two-motor system where steering is created by running left and right wheels at different speeds. Used by tanks, wheelchairs, and most small robots. See Section 3.1.
Motor Imbalance
When two motors don't spin at exactly the same speed despite receiving the same command. Every robot has this due to manufacturing variations. See Section 1.
Negative Speed Values
In motor commands, the minus sign means "backward" (not "slower"). -200 means "backward at speed 200." The magnitude |speed| is always positive. See Section 3.2.
Open-Loop Control
Send a command and hope for the best. No feedback about what actually happened. See Section 3.3.
TRIM
A small correction value added to one motor to compensate for imbalance. Like wheel alignment on a car. May vary slightly at different speeds. See Section 1 and Section 3.5.

Value What the motor does

Battery

int mv = readBatteryMillivolts(); // Returns millivolts (±10% accuracy)
// Convert: Volts = mv / 1000
// NiMH, 4 cells (what our robots run):
//   Fresh:  ~5400 mV   Plateau: ~4800 mV
//   Low:    <4200 mV   (recharge -- do not go lower)
// Alkaline reads ~6300 mV fresh: different chemistry.

Constrain

// From Arduino.h (included via Zumo32U4 library)
value = constrain(value, min, max);
// Examples:
constrain(450, -400, 400) → 400 // Too high, clamped to max
constrain(-500, -400, 400) → -400 // Too low, clamped to min
constrain(200, -400, 400) → 200 // In range, unchanged

Arrays

const int TEST_SPEEDS[] = {150, 200, 250, 300};
const int NUM_SPEEDS = 4;
// Slots are numbered from ZERO:
TEST_SPEEDS[0]  // 150  (first)
TEST_SPEEDS[3]  // 300  (last — one less than the count)
// The slot number can be a variable:
int speedIndex = 1;
int currentSpeed = TEST_SPEEDS[speedIndex];  // 200
// TEST_SPEEDS[4] is NOT an error — it returns garbage. See 8A.5.

Modulo (%) — Wrapping an Index

// % gives the REMAINDER of a division, not the division:
7 % 3  // 1
6 % 3  // 0
2 % 4  // 2
// A remainder is never as big as the divisor,
// so  x % 4  is always 0, 1, 2 or 3.
speedIndex = (speedIndex + 1) % NUM_SPEEDS;  // 0->1->2->3->0...
// Parentheses required: % binds tighter than +. See 8A.6.

int trimValue = 15; // Your robot's value
// Apply TRIM to motors:

int rightSpeed = BASE_SPEED;
motors.setSpeeds(leftSpeed, rightSpeed);

motors.setSpeeds(speed, speed); // Start motors

motors.setSpeeds(0, 0); // STOP! (never forget this!)
