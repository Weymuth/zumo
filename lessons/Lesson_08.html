📖 Section 1: The Drunk Robot Problem

Picture this: You've built your Zumo, calibrated your sensors, and you're ready to follow a line. You write what seems like perfectly logical code:

If the line is on the left, turn left.
If the line is on the right, turn right.
If the line is centered, go straight.

You set your robot on the track, press the button, and... disaster. Your robot lurches left, overcorrects right, swings back left, and zigzags down the course like it's had one too many battery charges.

This is the "bang-bang" problem—named after the jarring way the robot bangs back and forth between full-left and full-right corrections.

[VIDEO 8.1] Side-by-side comparison: Robot oscillating with bang-bang control vs. smooth line following with P-control
📘 Note: When Bang-Bang Works

Bang-bang control isn't always bad! It works great for binary actuators like relays, solenoids, or on/off switches where you only have two states. But for continuous actuators like motors that can run at any speed, proportional control gives much smoother results.

Now watch a competition robot. It glides along the line like it's on rails—smooth, fast, confident. The difference? Proportional control.

🤖 Real-World Connection

Proportional control is the "P" in PID control—the most widely used control algorithm in the world:

  • Cruise control — Adjusts throttle based on how far from target speed
  • Thermostats — Heat more when temperature is way below target
  • Drone altitude — Thrust harder when drifting further from target height

📖 LEARN: Bang-Bang vs. P-Control

Before P-Control, you probably wrote something like this:

if (position < 2000) {
// Line is left → turn left (HARD)
motors.setSpeeds(100, 300);
} else {
// Line is right → turn right (HARD)
motors.setSpeeds(300, 100);
}

This is called Bang-Bang Control—the robot is always turning hard left or hard right, never anything in between.

Bang-Bang Control P-Control
Only two states: full left or full right Infinite states: gentle to aggressive corrections
Jerky, zig-zag motion Smooth, curved corrections
Looks like: 🚗💥🚗💥🚗 Looks like: 🚗〰️🚗〰️🚗
Slow (constant overcorrection) Fast (efficient corrections)

The key insight: P-Control makes corrections proportional to the error. A little off-center? Small correction. Way off-center? Big correction. This is why it's called Proportional control.

3.1 The Proportional Control Solution

🔁 Builds on: the beep-speed formula from Lesson 5 — beepInterval = 700 - (value * 100) was output proportional to input. You have already written a P-term; today it steers.

The key formula:

correction = Kp × error

Where:

  • error = position − setpoint (how far off target)
  • Kp = proportional gain (how aggressively to correct)
  • correction = adjustment to motor speeds
🔑 Setpoint — The target value you want to maintain. For line following, the center setpoint is 2000 (range 0-4000).
🔑 Error — The difference between where you are and where you want to be.
🔑 Kp (Proportional Gain) — A tuning constant that scales error to correction. With position error ranging from -2000 to +2000 and typical Kp values of 0.1 to 0.3, your correction will range roughly from -600 to +600. Too low = sluggish. Too high = oscillates.
🔮 Looking Ahead: The Full PID

The "P" in P-control stands for Proportional—but it's actually just one part of a more complete system called PID:

  • P (Proportional) — What we're learning today: correct based on current error
  • I (Integral) — Fixes small persistent errors that P alone can't eliminate
  • D (Derivative) — Damps oscillation by predicting where error is heading

For line following, P-control alone is enough to get you round a course — which is why today stops here. But you will meet the other two letters: Lesson 15 is Advanced PID Control, where D damps the wobble you are about to spend Section 7 tuning out by hand, and I hunts the steady error that P alone can never quite kill. Today’s Kp is the foundation that lesson is built on.

3.2 Applying Correction to Motors

leftSpeed = baseSpeed + correction
rightSpeed = baseSpeed - correction

Understanding signed error: The error value tells you both how far and which direction to correct:

Situation Position Error Correction Result
Line RIGHT of center 3000 +1000 +100 (if Kp=0.1) Left faster → turns RIGHT
Line LEFT of center 1000 -1000 -100 (if Kp=0.1) Right faster → turns LEFT
Line CENTERED 2000 0 0 Both equal → STRAIGHT

💻 Section 5: Understanding the Code

Before you write code, you need to understand the core algorithm. Here's the proportional control formula translated from math to Arduino:

Mathematical Formula: 
correction = Kp × (position − setpoint)
Arduino Code: 
int error = position - LINE_CENTER;
int correction = Kp * error;

5.1 The Error Signal

The error is how far you are from your target. For line following:

🔑 Error = Current Position − Setpoint

Example: If position = 3200 and setpoint = 2000, then error = +1200 (line is 1200 units to the right)

📖 Why Signed Errors Matter

Notice the error is signed (positive or negative). This tells the robot not just how much to correct, but which direction:

  • Positive error (+1200) → Line is RIGHT → Turn right
  • Negative error (-1200) → Line is LEFT → Turn left
  • Zero error → Line is CENTERED → Go straight

5.2 Proportional Response

The proportional gain Kp scales the error into a motor correction:

Error With Kp = 0.1 Meaning
0 0 Line centered → no correction
±500 ±50 Slight offset → gentle adjustment
±1000 ±100 Moderate offset → medium adjustment
±2000 ±200 Far off → aggressive adjustment

5.3 Applying Correction to Motors

The correction is a steering adjustment added to one motor and subtracted from the other:

int leftSpeed = BASE_SPEED + correction;
int rightSpeed = BASE_SPEED - correction;
💡 Tip: Speed Limiting

Never let motor speeds exceed your MAX_SPEED constant. Use constrain() to keep values safe:

leftSpeed = constrain(leftSpeed, -MAX_SPEED, MAX_SPEED);

BRAIN CHECK 01 · MENTAL KNOWLEDGE CHECK — Answer From Your Head

That is the reading done — Sections 1 through 5. Before you write a line of followLine(), answer these five from your head: no scrolling back, no editor open. Then click to compare. If your answer and the reveal disagree, the section number tells you where to re-read.

1. Your first line-follower turned hard left or hard right and nothing in between. What is that controller called, and what kind of hardware is it actually right for? (§1)

Bang-bang control — named for the way the robot bangs back and forth between full-left and full-right. It is the right choice for binary actuators: relays, solenoids, on/off switches, things that only have two states anyway. A motor is a continuous actuator — it can run at any speed — so bang-bang throws away most of the hardware you already own.

2. Write the proportional formula, and say what each of its three parts means. (§3.1)

correction = Kp × error. error is position − setpoint, how far off target you are. Kp is the proportional gain, how aggressively to correct. correction is the adjustment applied to the motor speeds. Typical Kp runs 0.1 to 0.3: too low is sluggish, too high oscillates.

3. The correction is a single number. Which motor gets it added, and which gets it subtracted — and which way does the robot then turn? (§3.2)

leftSpeed = baseSpeed + correction and rightSpeed = baseSpeed − correction. The left motor gets the plus. With the line to the right of center the error is positive, so the left wheel speeds up and the robot turns right — toward the line. A robot turns away from its faster wheel.

4. Why does the error have to be signed, rather than just a distance? (§5.1)

Because one number then carries both facts the robot needs. The size says how much to correct; the sign says which way — positive means the line is to the right, negative means to the left, zero means centered. Strip the sign and the robot knows it is off the line but not which way to steer.

5. Both motor speeds are BASE_SPEED plus or minus a correction, so either one can be commanded past the limit. What stops that? (§5.3)

constrain() — leftSpeed = constrain(leftSpeed, -MAX_SPEED, MAX_SPEED);. It clamps the result into the legal range before it ever reaches the motors, so a big error cannot command a speed the hardware will not honour.

// These values define your robot's hardware

8A.1 Function Parameters: Passing Information

When you write followLine(), you're reading the global currentKp value. But what if you wanted to follow the line with different Kp values at different speeds? That's where function parameters come in:

Current approach (hardcoded): 
void followLine() {
    int position = readLinePosition();
    int error = position - LINE_CENTER;
    int correction = currentKp * error;  // ← uses global currentKp
}
Better approach (parameterized): 
void followLine(float kp) {
    int position = readLinePosition();
    int error = position - LINE_CENTER;
    int correction = kp * error;  // ← uses parameter kp
}
🔑 Function Parameter — A value you pass INTO a function that the function can use. Allows flexibility without global variables.

void handleRobotControl() {
    // 1. READ the current state
    int position = readLinePosition();
    // 2. CALCULATE error
    int error = position - SETPOINT;
    // 3. APPLY proportional formula
    int correction = Kp * error;
    // 4. CLAMP the output
    correction = constrain(correction, -MAX_CORRECTION, MAX_CORRECTION);
    // 5. CONVERT to motor commands
    int leftSpeed = BASE_SPEED + correction;
    int rightSpeed = BASE_SPEED - correction;
    // 6. SEND to motors
    motors.setSpeeds(leftSpeed, rightSpeed);
}

  } else {
    adaptiveKp = 0.25;   // Aggressive - way off
  }
  int correction = adaptiveKp * error;
  int leftSpeed = BASE_SPEED + correction;
  int rightSpeed = BASE_SPEED - correction;
  leftSpeed = constrain(leftSpeed, -MAX_SPEED, MAX_SPEED);
  rightSpeed = constrain(rightSpeed, -MAX_SPEED, MAX_SPEED);
  motors.setSpeeds(leftSpeed, rightSpeed);
}

Swap it in for followLine(); in the visible branch. Tune the two band edges (500, 1000) and three gains on your own track — the reveal's numbers are a starting point, not an answer.

🔁 Builds on: the beep-speed formula from Lesson 5 — output proportional to input, one more time. There it set a beep. Here it sets the throttle.

🎯 THE GOAL

One BASE_SPEED is a compromise: fast enough to win the straights, slow enough to survive the curves. Challenge 1 found that compromise number. Now remove the compromise — let the error set the throttle. Centered means full speed. Far off the line means the robot slows itself down. Two proportional controllers running on the same error: one steers, one throttles.

🧠 THE LOGIC

1. position, error, correction — UNCHANGED (the steering P)
2. speed = BASE_SPEED - KS × |error|   (the throttle P)
3. IF speed < MIN_SPEED: speed = MIN_SPEED   (the floor)
4. left = speed + correction, right = speed - correction
5. constrain both, setSpeeds — UNCHANGED

const float KS = 0.03;        // Throttle gain - how hard error brakes the robot

main.cpp:

void followLine() {
  int position = readLinePosition();
  int error = position - LINE_CENTER;
  int correction = currentKp * error;

  // THE THROTTLE P - speed falls as the error grows
  int speed = BASE_SPEED - KS * abs(error);
  if (speed < MIN_SPEED) {
    speed = MIN_SPEED;
  }

  int leftSpeed = speed + correction;
  int rightSpeed = speed - correction;
  leftSpeed = constrain(leftSpeed, -MAX_SPEED, MAX_SPEED);
  rightSpeed = constrain(rightSpeed, -MAX_SPEED, MAX_SPEED);
  motors.setSpeeds(leftSpeed, rightSpeed);
}

The arithmetic of the throttle: error tops out at 2000. At KS = 0.03 the biggest possible slowdown is 0.03 × 2000 = 60 — a BASE_SPEED of 150 dips to 90 in the worst moment, and the floor catches it at 100. Raise KS and the robot brakes harder for its mistakes; raise it too far and it crawls through every wobble.

Three ways this goes wrong:

  • Used error instead of abs(error): the robot speeds UP when the line drifts one way and brakes the other way. Slowing down has no direction — that is what the absolute value is for.
  • No floor: a hard corner at a hot KS can drive speed to zero — the robot stalls in exactly the curve it most needed to finish. MIN_SPEED is the promise that it always keeps moving.
  • Tuned KS before Kp: the throttle rides on the steering. A wobbling robot manufactures fake error and brakes for corners that are not there. Wiggle Test first (Challenge 2), then KS.

The tuning ritual, in order: tune Kp until stable (Challenge 2) → raise KS until curves feel deliberate instead of desperate → then raise BASE_SPEED past the maximum you recorded in Challenge 1. That old number was the compromise. The compromise is gone, so your straight-line ceiling is higher than it was — write both numbers in your notebook, side by side.

Notice what you built: Challenge 5 picked between three gains by error band — steps. This slides continuously — a ramp. Same idea, smoother tool. 🔍 Bonus: Five Line-Following Mysteries

Detective work. Each Maker link below opens the finished build with one deliberate defect planted. The routine: upload it, watch the symptom, predict the culprit before opening a single file, find it, fix it, prove the fix on the track. Every defect here is one the robot can't explain to you — the symptom is all you get, exactly like real debugging.

Mystery 1: Backwards Correction

→ load the sabotaged build — upload and start it on a straight line, on the floor. The instant it drifts a hair off center, it snaps hard away from the line and spirals off. Why away — and why so violently?

💡 Answer

Two characters, one function. The planted lines in followLine():

  int leftSpeed = BASE_SPEED - correction;
  int rightSpeed = BASE_SPEED + correction;

The signs are swapped, so every correction steers away from the line — which grows the error, which grows the correction. Proportional control with the sign flipped isn't weak, it's a runaway. Swap the signs back.

Mystery 2: The Straight-Liner

→ load the sabotaged build — flawless on the straightaway, sails serenely off every curve, no correction whatsoever. Before opening any file: read the status screen. It has been telling you the answer the whole time.

💡 Answer

The screen says Kp: 0.00. The planted line:

float currentKp = 0.0;           // Live-tunable copy of KP

Gain zero → correction zero → a robot that only drives straight. Pressing C revives it until the next reboot — live tuning treats the symptom, the initializer is the disease. Restore float currentKp = KP;.

Mystery 3: The Uncalibrated Run

→ load the sabotaged build — the screen says "Calibrating..." — but the robot never spins — then the instant you press B to go: LINE LOST, while sitting dead-center on a perfect line. The display is lying to you. About what?

💡 Hint

The calibrateLineSensors(); call was deleted from setup — the choreography around it survived, so the screen narrates a calibration that never happens. The library's own source says what happens next: "if not calibrated, do nothing" — readCalibrated() refuses to write, sensorValues stays all zeros, the sum never beats the threshold, and the robot is blind by protocol. Put the call back — and remember Step 5: calibration isn't ceremony, it's what makes the 0–1000 scale exist.

Mystery 4: The Eternal Gap

→ load the sabotaged build — floor only, spotter ready — this one does not stop on its own. It follows fine, but at the first gap it coasts straight… and keeps coasting. Forever. What gave up: the gap logic, or the number it was given?

💡 Answer

The logic is perfect. The planted constant:

const unsigned long MAX_GAP_TIME = 500000;  // Max milliseconds to cross a gap

500,000 ms is an eight-minute gap allowance — the timeout exists and can essentially never fire. A safety limit that can't trigger is indistinguishable from no safety at all; that's the whole lesson. Restore 500.

Mystery 5: The Blind Robot

→ load the sabotaged build — calibration runs correctly this time — real spin and all — and it still declares LINE LOST instantly, parked on a jet-black line. Same symptom as Mystery 3, so: same cause? Prove your answer before you look.

💡 Answer

Different culprit entirely. The planted constant:

const int LINE_LOST_THRESHOLD = 5001;    // Calibrated sum below this = no line

Five sensors × 1000 max = a highest possible sum of 5000. The visibility test can never pass — not on any line, ever. Same symptom as Mystery 3, opposite end of the pipeline: one starves the reading, the other sets an impossible bar. Same symptom ≠ same cause is the most valuable sentence in debugging. Restore 200.

redefinition of 'Zumo32U4LineSensors lineSensors' — a compiler error inside RobotSensors.cpp — when the header lost extern and the .cpp still defines it, so one file saw two creations.

5. In handleGap(), why must the line-visible branch reset gapStartTime to 0 — and what breaks on the second gap if it does not? (§6 Step 8)

Show answer

The clock is stamped only on the first blind frame: if (gapStartTime == 0) gapStartTime = millis();. If the visible branch never clears it, the stamp from the first gap survives, so on the second gap millis() - gapStartTime is already far past MAX_GAP_TIME. The robot declares LINE LOST on the very first blind frame, before it has coasted anywhere — and the gap it could have crossed the first time now stops it.

6. driveDistance() gets TRIM and followLine() must not. What is the one-question test that tells them apart? (§6 Step 8)

Show answer

Is anything watching? If not, it needs TRIM. driveDistance() is an open loop — nothing reads the floor, so motor bias goes uncorrected and TRIM is what keeps it straight. followLine() is a closed loop: it reads the line fifty times a second and correcting bias is already its job, so TRIM there just gives the P-term a constant to spend the day undoing. handleGap() gets TRIM because a blind robot is open loop again.

🔀 map() — RESCALING A NUMBER

map() takes a number living in one range and returns where it would sit in a different range. It is the tool for turning a sensor reading into something else — a screen column, a speed, a bar length.

map(value, fromLow, fromHigh, toLow, toHigh)

map(2000, 0, 4000, 0, 20)   // 2000 is halfway through 0-4000
                            // returns 10  - halfway through 0-20

Read the five arguments as one sentence: take this value, which lives between fromLow and fromHigh, and tell me where it lands between toLow and toHigh. The first three describe where the number comes from; the last two describe where you want it.

  • Returns an int — the fraction is dropped, so a result of 10.7 comes back as 10.
  • The output range may be smaller than the input range, larger, or reversed — map(pos, 0, 4000, 20, 0) flips the direction.
  • It does not clamp. A value outside the input range maps to a result outside the output range, so pair it with constrain() when the answer must stay on screen.
