How a letter becomes electricity Lesson 2

In Lesson 2 you wrote display.print(F("LESSON 2")) and eight characters appeared on the OLED. The robot does not have letters in it. It has voltages that are either high or low. Something in between turned one into the other, and it is worth seeing.

Step 1 — every character is secretly a number

A long time ago engineers agreed on a lookup table so that every machine would use the same number for the same character. It is called ASCII, and it is nothing more sophisticated than an agreed-upon list:

CharacterASCII number
A65
B66
a97
0 (the character zero)48
space32

Notice that '0' is 48, not 0. The character zero and the number zero are different things, which is why you cannot do arithmetic on text without converting it first.

Try it on your robot. A char in C++ is just a small number wearing a costume. This compiles and prints 65: 
char letter = 'A';
Serial.println((int)letter);   // 65

Step 2 — every number is a row of switches

The chip has no way to store “65.” It has switches that are on or off. So it writes 65 using eight of them, where each position is worth double the one to its right:

128   64   32   16    8    4    2    1
  0    1    0    0    0    0    0    1

      64 + 1 = 65  ->  the letter 'A'

That is binary, and the recipe is greedy: walk left to right, and at each slot ask “does this fit in what is left?” If yes, write 1 and subtract. If no, write 0.

Work 25 through it: 128 no, 64 no, 32 no, 16 yes (9 left), 8 yes (1 left), 4 no, 2 no, 1 yes (0 left). Answer: 00011001.

Eight switches is a byte, and it holds 0 through 255. That number should look familiar — it is the same 8-bit ceiling behind a great many limits you will meet in embedded work.

Step 3 — the switches become voltage over time

To send a byte down a single wire, the two ends agree on a speed and the sender flips the line high and low in time with a clock. The receiver samples at the agreed rate and reassembles the bits. That agreed speed is the baud rate — the 115200 in Serial.begin(115200), measured in bits per second. Both ends must use the same number, or the receiver samples at the wrong moments and reassembles bits that were never sent. That is the actual mechanism behind the “Serial Monitor shows garbage” row in Lesson 1's troubleshooting table.

Why this matters past the trivia. Every OLED string, every Serial.println(), and every byte of your program on its way down the USB cable is doing exactly this. When Lesson 16 tells you a string costs 18 bytes, it is counting characters — one byte each, plus one invisible zero on the end marking where the text stops.

What F() is really doing Lessons 2, 12, 16

Lesson 2 tells you that F() keeps a string in flash instead of copying it into SRAM. True, and enough to work with. The question it leaves alone is why the chip would ever copy it in the first place. The answer is that your robot's processor is built on a fundamentally different plan than the computer you are typing on.

Two memories that cannot see each other

Your laptop uses a von Neumann design: one memory space holding both program and data, one set of instructions for reaching it. A string is just bytes at an address, and the same instruction reads it whether it is code or text.

The ATmega32U4 uses a Harvard design instead. Program and data live in physically separate memories, reached by different machine instructions:

FlashSRAM
Size on your Zumo28,672 B usable~2,560 B
Survives power-offYesNo
Written byUpload onlyYour program, constantly
Read withLPM instructionLD instruction

That last row is the whole problem. A pointer on this chip is just a number, and the number 300 means two different bytes depending on which instruction you use to fetch it. So when a function like print() receives a pointer, it has no way to tell which memory it points into.

The compiler's cowardly, sensible fix

Faced with that ambiguity, the toolchain does the only thing that always works: at power-on, before setup() runs, it copies every string out of flash into SRAM. Now every pointer means SRAM, print() is safe, and your code works. The cost is that a copy of all your text is squatting permanently in the memory you needed for variables.

F() is how you refuse that deal. It is a macro that casts the string to a distinct type — __FlashStringHelper* — that exists purely so the compiler can tell the difference:

display.print("Ready");      // const char* -> "read from SRAM"
display.print(F("Ready"));   // __FlashStringHelper* -> "read from flash"

Same text, different type. C++ picks a different version of print() based on that type, and the flash version reads characters one at a time with the LPM instruction instead of expecting a copy in SRAM. That is the entire trick: F() does not move anything — it changes which print() gets called.

Why nobody on a laptop has heard of this. Desktop C++ has no F() because von Neumann machines have no ambiguity to resolve. If you go looking for this online you will find Arduino and AVR pages and nothing else. It is not a C++ feature. It is a workaround for a hardware split, and it disappears the moment you move to a chip that does not have one.

What actually happens when you press Build Lessons 1, 12, 16

Lesson 1 calls it “compiling.” Lesson 12 mentions that “the linker noticed” an unused function and threw it away. Those are two different programs, and there are two more you have never been introduced to. Knowing which one is complaining tells you where the mistake is.

Four programs, in order

1. The preprocessor runs first and does not understand C++ at all. It is a text substitution engine. It finds every #include and pastes that entire file in place of the line; it finds every #define and swaps the text. Its output is one enormous file with no # lines left in it.

Its errors sound like: Zumo32U4.h: No such file or directory. The library is missing or misspelled. Nothing has been compiled yet.

2. The compiler takes that file and translates it into machine instructions for the AVR. This is the stage that reads your syntax, so it is the one that catches missing semicolons, unmatched braces, and undeclared names. It works on one file at a time and knows nothing about the others — which is exactly why Lesson 7's headers exist.

Its errors sound like: expected ';' before · 'calibrateSensors' was not declared in this scope.

3. The linker collects the compiled pieces and wires them together, matching every function call to the one definition of that function. It is the first stage that sees your whole program at once.

Its errors sound like: undefined reference to — you promised a function existed and never wrote it. Also: region 'text' overflowed, the Lesson 16 wall.

This is the Lesson 12 moment. The linker walks outward from main() asking “can this ever run?” A function nothing calls is unreachable, so it never gets written to the binary at all. That is why writing turnDegreesGyro() did not make your program one byte bigger. The linker is also the only stage that could possibly know that — the compiler saw only one file.

4. The uploader converts the binary to Intel HEX (a text format, oddly), talks to the bootloader over USB, and writes it into flash. The bootloader is that 4 KB you do not get to use.

Why eight files instead of one Lesson 7

Lesson 7 hands you the rules: declarations go in .h, definitions go in .cpp, shared variables get extern. Follow them and it compiles. The reasoning underneath is one fact from the previous entry, applied over and over.

The compiler sees one file at a time

Each .cpp is compiled in complete isolation — a translation unit. When Movement.cpp calls readLinePosition(), the compiler has never heard of it, because that function lives in a file it is not currently looking at. It cannot go peek. It has one job, one file.

So you leave it a note. A header is a file of promises: this function exists, here is its shape, trust me and carry on. The compiler generates a placeholder call and marks it unresolved. Later the linker — which does see everything — finds the real definition and fills in the address.

This is the same idea as the prototype in Lesson 2. A prototype lets you call a function defined lower in the same file. A header lets you call one defined in a different file entirely. Identical trick, wider scope: declare the shape now, supply the body later, let the linker connect them.

Why extern exists

Variables have the same problem plus one extra hazard. If two .cpp files both say int robotSpeed;, you have created two different variables with the same name, and the linker will refuse the job. So you split it: one file defines it, and the header declares it with extern, which means “this exists somewhere else, do not make another one.”

// Config.h  - the promise, seen by everyone
extern int robotSpeed;

// Config.cpp - the one real variable
int robotSpeed = 200;

What you actually bought

  • Change one file, rebuild one file. Editing Movement.cpp does not recompile the other seven.
  • Errors get a return address. A line-sensor bug lives in Sensors.cpp, not somewhere in 800 lines.
  • The header becomes the documentation. Reading Movement.h tells you what movement can do without reading how.
  • You can hand someone a file. Your teammate implements against the header while you keep working. That is the actual reason professional codebases are built this way.

Using Fixed Point Lessons 8, 12, 15

Lesson 12 §8A.3 already showed you fixed point in action: the gyro stores its running angle as a plain integer where 229 units = 45°, because the ATmega32U4 has no floating-point hardware and emulating it thousands of times per turn would eat the whole loop. That was Pololu's code, and the lesson tells you it is none of your business.

This entry is the same idea pointed at your code — specifically at float Kp = 0.10; from Lesson 8, which is doing exactly the expensive thing L12 warned about, in the tightest loop you own.

What a float actually costs here

When you write correction = Kp * error;, the compiler substitutes a call into a software library that assembles the answer out of integer operations. Rough shape of it:

OperationRoughly
int add1 cycle
int multiply2 cycles
float add~100+ cycles
float multiply~140+ cycles

Two orders of magnitude. The float library also costs you a chunk of flash the moment you use it — which is why Lesson 16's byte ladder is as high as it is.

Fixed point: decimals without floats

The trick is to stop storing the decimal at all and agree to remember where it goes. Multiply everything by 100, do integer arithmetic, divide at the very end:

// float version
float Kp = 0.10;
correction = Kp * error;

// fixed-point version: Kp scaled by 100
const int KP_X100 = 10;              // 0.10 * 100
correction = (KP_X100 * error) / 100;

Same answer, integer speed. The scale factor lives in your head and in the constant's name — which is why KP_X100 is named that way and not KP.

What it costs you. Integer division truncates, so error accumulates. Multiply first and divide last, or you throw away precision you needed. And a scaled value overflows sooner: an int stops at 32,767, so KP_X100 * error with a large error can wrap around to a negative number and drive your robot the wrong way. That failure is silent.

Should you convert? Not while you are learning — floats are readable, and in Lesson 8 your loop has time to spare. Reach for this when the byte ladder is against the ceiling in Lesson 16, or when the Lesson 15 loop timing will not come down. L12 made this choice for the gyro because that code runs thousands of times per turn; whether your control loop has crossed the same line is a measurement, not a guess.

The deeper lesson, which L12 states better than I can. Choosing your units well can make an entire class of bug impossible to write — the gyro's angle wraps correctly at 360° for free, because of the unit, with no code handling it. Fixed point is not only a speed trick. It is a chance to pick units that do work for you.

What an object is, one level down Lesson 2

Lesson 2 says an object is a named bundle of memory plus the commands that work on it, and that you talk to it with name-dot-command. That is accurate. Here is the layer underneath — enough to explain the errors you will actually hit, and no further.

Class and instance are different things

Zumo32U4Motors is a class — a description, written by Pololu, that lives in the library. It occupies no memory in your robot and controls nothing. It is a blueprint.

motors is an instance — an actual object built from that blueprint when you wrote Zumo32U4Motors motors;. It has an address. It is the thing that does something.

The distinction sounds academic until you read an error message. 'Zumo32U4Motors' has not been declared means the compiler cannot find the blueprint — your #include is missing. 'motors' was not declared in this scope means the blueprint is fine but you never built one, or you built it somewhere this code cannot see.

Why the dot

When you call motors.setSpeeds(100, 100), the function needs to know which object to act on. The dot supplies it. Behind the scenes the compiler passes the object's address as a hidden first argument, which is why the same setSpeeds code can drive any number of motor objects without confusion.

That is also why Zumo32U4Motors.setSpeeds(100, 100) is an error. You handed it the blueprint. There is nothing there to drive.

Why declaring two is a bug, not a duplicate

Zumo32U4Motors motors;      // in main.cpp
Zumo32U4Motors motors2;     // somewhere else - DON'T

This compiles. Both objects work. And they both write to the same physical motor-driver pins, with no idea the other exists — so whichever ran last wins, and the resulting behavior looks like a logic bug rather than a structural one. An object is a handle to hardware, not the hardware itself. One handle per thing, declared once, up top.

Where to stop. If you go reading about C++ objects online you will hit constructors, destructors, inheritance, new, and smart pointers within about two screens. Almost none of that applies here: dynamic allocation is avoided on a chip with 2.5 KB of SRAM, and this book never needs it. Objects in this book are exactly what Lesson 2 says — declared once at the top, alive for the whole run, talked to with a dot.
